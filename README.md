# Netflix-Movie-Project-Deployment-documentation
A README step-by-step project walkthrough

This project documents my hands-on deployment of a full-stack Netflix Movie Application using **GitHub, GitHub Actions, Docker, AWS ECR, AWS EC2, MongoDB Atlas, and Portainer**.

The goal of this project was not only to run the application, but to build a complete deployment workflow where application changes are automatically built as Docker images, pushed to Amazon ECR, and deployed to an EC2 server.

# 🔄 Automating Continuous Deployment

## 36. Adding the Deployment Stage

### What I did

Initially, GitHub Actions handled only:

```text
Build → Push to ECR
```

I extended the workflow by adding a second `deploy` job that runs only after `build-and-push` succeeds.

The new pipeline became:

```text
GitHub Push
     ↓
Build Docker Image
     ↓
Push Image to ECR
     ↓
Deploy to EC2
     ↓
Pull New Image
     ↓
Replace Previous Container
     ↓
Updated Application Running
```

### What I achieved

I transformed the workflow from a CI-only pipeline into an automated CI/CD deployment workflow.

![CI CD Jobs](screenshots/36-cicd-jobs.jpeg)

# 🧩 Challenges I Encountered

Throughout this project, I encountered and resolved several practical DevOps issues:

- GitHub push permission and authentication problems.
- Missing AWS GitHub Actions secrets.
- Missing `AWS_REGION`.
- Incorrect Docker tag syntax.
- ECR authentication errors.
- YAML indentation and duplicate workflow-key errors.
- AWS CLI not being available in the non-interactive deployment shell.
- An expired ECR authentication token.
- Frontend pointing to an old backend EC2 IP.
- Synchronizing local and remote Git history.
- Passing `MONGODB_URI` securely to the backend container.
- Portainer initial setup timeout.
- Testing and distinguishing a Spring Boot root-route 404 from an actual application failure.

Solving these issues helped me understand that DevOps is not simply about writing deployment commands. It also involves troubleshooting the interactions between source control, CI/CD, cloud permissions, networking, containers, databases, and application configuration.

# 🔐 Security Practices

Throughout the project:

- AWS credentials were stored as GitHub Actions secrets.
- MongoDB credentials were passed using the `MONGODB_URI` environment variable.
- SSH private keys were stored as GitHub secrets for automated deployment.
- Credentials were not intentionally committed to the repositories.

For a production environment, I would additionally restrict EC2 security-group access, restrict MongoDB Atlas network access, use an Elastic IP or domain, configure trusted HTTPS certificates, and expose the application through ports `80/443` behind a reverse proxy.
